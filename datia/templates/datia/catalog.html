Sincronización Incremental (Resumen Ejecutivo)

Copia solo documentos modificados desde MSSQL (7 días por defecto) y recalcula métricas en Postgres.

  • Ventana incremental: 7 días (cutoff por checkpoint last_fecha).
  • Checkpoint: datia_sync_checkpoints (empresa, ejercicio, tipo, last_fecha).
  • Cabeceras: INSERT… ON CONFLICT DO UPDATE; Líneas: DELETE + COPY por documento.
  • Agregación local a metrics_* (ventas y compras) desde datiadb_*.
  • Endpoints: /api/etl/incremental/{sales|purchases|financial}; Commands: datia_sync_incremental_*.
  • Parámetros clave: empresa, ejercicio, days_back, fast_bulk, sync_type.
  • Garantía: solo documentos con fecha ≥ cutoff; métricas coherentes e idempotentes.

Arquitectura de la API

La API de Datia se expone bajo /api/ mediante Django Ninja y se organiza en routers por dominio. El acceso se realiza siempre sobre sesión autenticada de Django (cookies + CSRF).

  • Base: /api/ – Instancia única de NinjaAPI definida en datia/api/api.py.
  • Subrutas principales: /datia, /etl, /patterns, /issues, /features, /template, /system, /mobile, /financial, /inventory, /ai, /config, /auto-training.
  • Estilo: JSON sobre HTTP (REST simple); sin versionado en URL (versión lógica 2.0.0 en la instancia de Ninja).
  • Autenticación: Sesión Django; vistas críticas decoradas con @login_required y protección CSRF activa.
  • Ámbito: Entorno on-premise controlado; no se exponen endpoints públicos sin autenticación salvo casos explícitos documentados.

Contratos JSON y Manejo de Errores

Los endpoints utilizan dos patrones principales de contrato JSON: esquemas tipados de Ninja y respuestas manuales con campos status y message.

  • Esquemas Ninja: Endpoints como /api/features/ y /api/issues/ devuelven listas de objetos tipados (FeatureSchema, IssueSchema) con campos id, title, description, status, etc.
  • Patrón status/message: Endpoints de sistema (por ejemplo, cambio de contraseña o contexto semántico) responden con {"status": "success" | "error", "message": "..."} y códigos HTTP adecuados (200, 400, 401, 500).
  • Validación de entrada: Se comprueban campos obligatorios y tipos (por ejemplo, empresa debe ser numérica entera) devolviendo status="error" en caso de violación.
  • Errores IA: El router de IA devuelve estructuras enriquecidas (type, text, details) para representar ambigüedad, timeouts o problemas de generación de SQL.

Seguridad y Restricciones

La capa de seguridad combina autenticación de sesión, control de origen (CSRF) y políticas estrictas sobre qué datos pueden consultarse desde la IA y las herramientas de introspección.

  • CSRF y proxies: CSRF_TRUSTED_ORIGINS y SECURE_PROXY_SSL_HEADER configurados para acceso seguro desde túneles (ngrok, Cloudflare, etc.) sin desactivar protección CSRF.
  • Permisos: Endpoints sensibles (por ejemplo, /api/config/global) requieren usuario de staff; el acceso a empresas se filtra mediante UserEmpresaPermission.
  • Restricción IA: El generador SQL de IA sólo puede consultar tablas permitidas (DatiaDB_* y dominios autorizados); cualquier violación produce una respuesta de alerta de seguridad en lugar de ejecutar la consulta.
  • Operaciones destructivas: Endpoints como el factory reset semántico están deshabilitados por defecto y devuelven código HTTP 410 con mensaje de error, evitando borrados accidentales.
  • Normalización de IDs: Identificadores como empresa se normalizan a entero para garantizar consistencia y evitar ataques por inyección de parámetros.

DSLQueryExecutor

services/ai/dsl_query.py

Ejecutor de consultas IA basadas en un DSL seguro compilado a Django ORM, trabajando solo sobre métricas agregadas en Postgres (sin tocar tablas crudas históricas).

Fuentes válidas (source):
  • metrics_mensual: métricas mensuales (ingresos, margen, etc.).
  • metrics_clientes: métricas agregadas por cliente.
  • metrics_articulos: métricas agregadas por artículo.
  • financial_acumulados: acumulados contables por cuenta/periodo.
Ejemplos de consultas soportadas:
  • Ventas mensuales del año → source=metrics_mensual, group_by=['mes'], agregación sobre importe_neto_total.
  • Top clientes por importe neto → source=metrics_clientes, group_by=['cliente'], SUM sobre importe_neto_total, order_by desc.
  • Evolución del margen por artículo → source=metrics_articulos, group_by=['articulo'], time.group='month'.
  • Ingresos totales por trimestre → source=metrics_mensual o financial_acumulados, time.group='quarter'.

NF‑Docker: Contenerización Segura de Datia

Nueva funcionalidad para habilitar despliegues en Docker de forma segura y reproducible, sin afectar el funcionamiento actual.

Requisitos Previos

  • Docker Desktop 29+ (Windows) con daemon activo
  • Acceso a repositorio y variables de entorno (SECRET_KEY, DATIA_ANALYTICS_URL, MSSQL_*)
  • Proxy/Firewall para publicación controlada de puertos 8000/8001

Configuraciones Recomendadas

  • Usuario no‑root, no‑new‑privileges, cap_drop: ALL
  • Sistema de ficheros de solo lectura; logs en volumen dedicado
  • Red bridge privada; publicación externa solo vía reverse proxy
  • Variables de entorno seguras; sin valores por defecto inseguros

Pasos de Implementación

  1. Construir imagen: docker build -t datia-web:secure .
  2. Escanear CVEs: docker scout cves datia-web:secure o trivy image
  3. Configurar proxy/ACL y DNS; definir ALLOWED_HOSTS y CSRF_TRUSTED_ORIGINS
  4. Despliegue controlado con docker-compose en red privada

Mejores Prácticas

  • Versionar por digest y fijar versiones de dependencias
  • CI con escaneo semanal de imágenes y del repo (Trivy/Scout)
  • Healthchecks internos, sin exponer endpoints de salud a Internet
  • Logs a stdout o volumen; rotación gestionada por el host

Ejemplo Dockerfile

FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1
RUN adduser --disabled-password --gecos "" datia
WORKDIR /app
COPY requirements.txt /app/requirements.txt
RUN apt-get update && apt-get install -y --no-install-recommends build-essential gcc unixodbc-dev libpq-dev && \
    pip install --no-cache-dir -r /app/requirements.txt && \
    apt-get clean && rm -rf /var/lib/apt/lists/*
COPY . /app
RUN chown -R datia:datia /app
USER datia
ENV DJANGO_SETTINGS_MODULE=config.settings
ENV DATIA_LOG_FILE=/app/logs/datia.log
CMD ["python","manage.py","serveboth"]

Comandos Esenciales

  • docker build -t datia-web:secure .
  • docker compose up -d (despliegue controlado; requiere proxy)
  • docker scout cves datia-web:secure / trivy image datia-web:secure
  • docker/docker-bench-security para auditoría CIS del host

Integración con Entorno Actual

Compatibilidad con el servidor dual (8000/8001) y configuración por entorno. Variables de entorno exigidas: SECRET_KEY, DATIA_ANALYTICS_URL, MSSQL_*. Logging configurable vía DATIA_LOG_FILE para cumplir con FS de solo lectura.

Consideraciones de Seguridad

  • Usuario no‑root, sin privilegios adicionales; rootfs read‑only
  • Puertos 8000/8001 detrás de reverse proxy y ACLs
  • ALLOWED_HOSTS y CSRF_TRUSTED_ORIGINS ajustados a dominios reales
  • Escaneo de CVEs continuo y rotación de secrets

Referencias Cruzadas

  • CLI: manage.py runserver / serveboth (Servidor dual 8000/8001)
  • API: /api/system/mobile_server (control del servidor móvil)
  • Seguridad: Auditoría CIS Docker, Trivy/Docker Scout
